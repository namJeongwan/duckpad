### 6.1 Unborn same-candidate reviewer reproduction

In a clean temporary unborn repository, the reviewer key and `allowed_signers` entry were externally created first, while the versioned registry began only in the candidate. The same root candidate introduced `/reviewer/genesis` into `docs/parity/reviewer-identities.v1.json`. Current `approval_registry_bytes` selected that candidate tree as the genesis approval registry. The reviewer then signed and the candidate passed verify, commit, and audit:

```text
PASS: candidate d2aecc9d52f0a99c8ffcb2731e9f33d5732715044208b98b73e87f4c357fcca0 has an independent signed review
PASS: audited 1 commit(s)
commit: 48057c9357d2e0d4f2139366e13fb5b40abeaac7
```

This does not challenge external key custody or the same-UID threat boundary. It proves a narrower policy defect: for `ROOT`, signer eligibility comes from reviewer metadata introduced by the exact candidate being approved, contrary to the stated “candidate-added reviewer is usable only after onboarding” invariant.

### 6.2 Reuse of signed parity evidence after contract mutation

The positive release fixture was signed normally. Without changing the candidate or any attestation, a temporary copied baseline then changed feature acceptance, G1 acceptance, and category weights from `C1=16/C8=9` to `C1=24/C8=1`, retained the same `baseline_version`, and recomputed only the unsigned sidecar. Validation still returned `release_pass=true`:

```text
original baseline SHA-256: 01e02a0557fe01c2ab61992e58dea70305163c95aa6d7acb8672eb2daebdbb5053e
mutated baseline SHA-256:  f9a21c56f114051c888be1ab5fd2c71c39d4dc0c52d01be93e401b3f641b0bb0
reused attestation SHA-256: dd5a1d6ab1d2614117b0844f967fc9b605fed0e97f8b29cbfb7409df5229ed7f
mutated release_pass: true
```

The attestation binds `baseline_version`, candidate hash, subject IDs, and result bytes, but not an immutable digest of the scoring contract—weights, priorities, acceptance criteria, mappings, workflow acceptance, gates, and defect policy. A sidecar is integrity against accident, not independent authorization, because the builder can recompute it.

### 6.3 Malformed signed receipt reproduction

A correctly signed temporary receipt used JSON booleans for envelope/payload `schema_version` and unresolved counts, whitespace-only scope/validation entries, and `issued_at: "not-a-timestamp"`. `verify_candidate.py verify` returned exit 0 because Python treats `True == 1` and `False == 0`, and content/timestamp types are not validated:
